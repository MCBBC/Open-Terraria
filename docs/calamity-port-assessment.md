## 3. 结构性缺口(三个,按痛度)

1. **detour/IL 面(4.4k 行 ILEditing + 20 文件)**:灾厄改写原版判定/掉落/事件链。
   SW 的 L3 已决策不建 → 替代=把其中 ~20-40 个改动点逐条变成引擎显式钩
   (P1/P2 已验证的模式,纯工时无风险)。
2. **Calamity 内部框架**:灾厄不是裸写 tML——它有自己的 helper 层(CalamityGlobalNPC
   6k/CalPlayer 22k/弹幕编排/ stadium 判定/±状态机)。移植必须**连框架一起搬**,
   否则 4000 个内容文件没有地基。这是隐藏工程量的最大来源。
3. **自绘/特效**:灾厄大量 Draw 覆写 + shader 级效果。SW 的 SM2/GL 在引擎内,
   mod 侧只有 ModProj 自绘——需要给 mod 开 primitive/粒子/屏幕效果入口(新 API 面)。

## 4. 工时重算(★2026-10-05 校准修正:改用原版移植实证吞吐)

**校准锚修正**:初版误用「手搬」锚(700-1000 行/日→1,000-1,500 专注日)。
实际锚 = **本仓原版移植实证:491,530 行手写 TS / 约 2 个月 ≈ 8,000+ 行/日有效吞吐**
(AI 批量转译+对拍验证+集成全含)。灾厄同为开源完整 C# 源码,可翻译性与原版同级
→ 直接套用同一吞吐锚。

### 基线换算

836,592 行 ÷ 8,000+ 行/日 ≈ **100-105 个有效工作日 ≈ 3.5-4 个月批量转译**。

### 与原版移植的三处差异(加/减)

| 差异 | 影响 |
|---|---|
| ①无运行时 oracle(原版有真游戏对拍;灾厄只能源码+人工游玩验证) | **+1-2 月**(调试长尾,静默 bug 无金标兜底) |
| ②tML 运行时层(灾厄覆写的 hook 族由 tML base class 提供,需补 dispatch 层;P0-P6 已建 ~15 族,灾厄画像 ~30-40 族) | **+2-4 周** |
| ③灾厄的 IL/detour 对我们反而更易:我们拥有引擎 TS 源码,直接改自己的实现,无需 MonoMod | **-2-4 周**(抵消部分②) |
| ④资产(9,205 PNG 直转+1,043 音频走既有 opus 管线) | +1-2 周 |

### 重算结论

| 路径 | 工时 |
|---|---|
| **全量灾厄(AI 批量转译方法论)** | **4-7 个月**(批量 3.5-4 月+验证长尾 1-2 月+tML 层/资产/集成净额) |
| 灾厄-lite(数据全量+8-10 中档 Boss+硫海) | **4-7 周** |

## 5. 结论(修正版)

- **全量灾厄 ≈ 4-7 个月**(AI 批量转译方法论,与原版移植同量级)。初版
  「1,000-1,500 专注日/4-6 年」系手搬锚误判,作废——原版 49 万行 TS 两月收官
  的实证吞吐是唯一可信锚。
- 三条真实风险(与原版移植的差异,非难度天花板):①无 oracle=静默 bug 靠
  人工游玩+代码审查兜底;②tML hook dispatch 层缺口(灾厄画像 ~30-40 族,已建 15);
  ③灾厄自绘/shader 效果需按 SM2/GL 重写(不能照搬 HLSL)。
- 优势面:灾厄对原版的 IL/detour 改写,对我们=直接改自有 TS 源码(比 tML
  的 MonoMod 路线更直接);数据面(SetDefaults/配方/掉落)提取器直吃。
